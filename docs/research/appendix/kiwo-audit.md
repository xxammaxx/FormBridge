## 3. Significant Findings

1. **The PDF→model converter is vision-LLM-based and OpenAI-bound.** The entire `form_to_json` pipeline (the only path that turns a PDF form into the semantic model) runs on OpenAI GPT‑5.2 Vision with a Mistral fallback (`converter.py:43–44, 75–89`), while all other pipelines are Mistral. A single API key gating this pipeline is a deployment/privacy constraint (README.md:82–84: "Zusätzlich für OpenAI-basierte Verarbeitungspfade, insbesondere die PDF-zu-Formularmodell-Pipeline: OPENAI_API_KEY").
2. **Clever marker-based visual field mapping instead of coordinates.** Phase 4 stamps marker strings into a copy of the PDF, rasterizes it, and lets the vision LLM associate rendered markers with labels (`phase4_mapping.py:47–50, 154–203`). This produces label→attribute mapping without storing any geometry; coordinates are simply absent from the data model (`schemas.py:73–110`).
3. **Field extraction presupposes fillable AcroForm PDFs.** `/TT` (label) and `/TU` (tooltip) keys plus `/Annots` widgets drive the FormFields layer (`phase3_fields.py:84–218`). A genuinely static/scanned form cannot yield a fillable output PDF — data collected beyond the PDF's field slots is documented as existing "only in form_values" (`schemas.py:309–314`).
4. **Conflict/provenance model is the strongest prior-art asset.** `FIELD_STATUS` with `conflict`/`validated`, `CONFLICT_RESOLUTION` (`form_values_merge.py:11–30`), `FieldSource` (`:33–48`), alternative values for user choice (`:355–384`), inline UI resolution with per-value source document (`FormularViewWidget.tsx:371–465`), plus row-level audit triggers into `audit_db.general_audit` (`user_formular.sql:96–182`).
5. **Confidence is declarative, not measured.** `_form_persistence.py:388–393` stamps every AI-suggested value with `"confidence": "high"`; the merge default is `"medium"` (`form_values_merge.py:743`). Only the VLM document check uses real numeric confidence with a threshold (`document_check/service.py:28, 406–427`).
6. **OCR/ASR/embeddings are all foreign cloud calls** (`document_ocr/service.py:4–11`, `multimodal.py:18`, `supabase_vec.py:62–67`) — relevant for any data-privacy-derived architecture claim.
7. **Naming archaeology:** the repo is internally branded OpenForm (`pyproject.toml:25` `name = "openform-backend"`, `compose.yaml:2` `name: openform`, `docs/ARCHITECTURE.md` title), while README/publiccode clarify KIWo is the published codebase and OpenForm the successor project (README.md:13, 197: "`kiwo_db` ist ein bewusst beibehaltener Legacy-Schemaname").
8. **Docs drift:** `services/backend/docs/TESTING.md` describes a test layout (subpackages, no global conftest) that contradicts the actual tree (flat tests + `conftest.py` present); the FitConnect mention (`TESTING.md:12`) is the sole trace of the FIM-adjacent ecosystem and is not backed by code.

## 5. Assessment

**Does KIWo implement a "legacy-static-PDF → versioned-FIM-field-IDs adapter" with provenance/confidence/human-review? No — but it implements a neighboring, partially overlapping system.**

- **Adapter from legacy (fillable) PDF → internal semantic model: YES.** The 7-phase `form_to_json` pipeline converts AcroForm PDFs into a 4-layer semantic model (FormFields → FormGraph → EngineConfig → ConditionsQueryTemplate; `docs/pipelines/01pipelineoverview.md:19–46`), and the frontend fills the original PDF from that model (`pdf/route.ts:33–47`). However the *static, non-fillable* PDF case yields no fillable output (finding #3), so "legacy-static-PDF" as input is only half-covered (semantic understanding yes, filling no).
- **Versioned FIM field IDs: NO.** The only versioning is internal artifact versions (EngineConfig v4.0, CQT v2.0.0, form_values v3.0). FIM/XDF identifiers do not exist anywhere in the tree (matrix rows 5–6).
- **Provenance: YES, at value level.** Every attribute value carries a typed source with document name, timestamp and confidence class, plus DB-level audit triggers (matrix row 10). Mapping-decision provenance is absent.
- **Confidence: PARTIAL.** Enum-class and 0–1 scores exist, but extraction/mapping confidence is hardcoded rather than derived from the models (finding #5).
- **Human review: YES for extracted values.** A full conflict-detection → alternative-values → inline user resolution loop is implemented end-to-end (API, data model, UI). No caseworker review of template mappings.
- **External schema-valid output: NO** — validated internal JSON only.

For Feldexa 2.0's purposes: KIWo is genuine prior art for *PDF-form import via vision LLM, document OCR, field-level provenance with conflict resolution and human correction, and self-hosted data layers* — but it is **not** prior art for FIM/XDF schema import, FIM field-ID mapping, coordinate-based layout detection, calibrated uncertainty scoring, explicit abstention, or offline AI operation. Those gaps are exactly the successor project's stated roadmap ("Wiederverwendbare KI-Fähigkeiten ... OpenForm Core", README.md:190–193) and are not implemented in this repo.
